# 人のレビューの手引き(G6)

AI が書き、AI がレビューしたコードを、人が最後に確認するときの見方。1行ずつ全部読むのではなく、人にしか判断できないことに時間を使う。

P7 の関門 G6(高リスク差分の確認)で使う。対象の領域は [AGENTS.md](../AGENTS.md) の「人の承認が必要な領域」、レビュー強度の考え方は [flywheel_greenfield.md](flywheel_greenfield.md) の「レビュー強度の分類」を参照。

## 考え方

コードの細かい正しさ(書き方、命名、型、よくある不具合)は、自動チェックと AI のレビューに任せる。人は次の5つだけを見る。

| 観点 | 見ること |
| --- | --- |
| 意図 | 自分がやりたかったことと合っているか。AI はコードを見てレビューするので、要件とのずれに気づきにくい |
| 境界 | 外からの値がどこで入り、誰が何をできるか。ログイン、権限、他人のデータ |
| 不可逆 | 間違ったときに元に戻せるか。削除、データ変更、お金、公開範囲、権限付与 |
| 証拠 | テストが本当に大事なことを確かめているか。実装に合わせて書いたテストは、何も守らない |
| 欠落 | 書かれていないもの。新しい入口に認証が付いていない、エラー時の処理が無い、など。差分に出てこないので見落としやすい |

## 土台にしている考え方

「AI が書き、人が最後に確認する」流れに特化した定番の枠組みは、まだ無い。次の考え方を組み合わせている。

| 名前 | 中身 | この手引きでの使い方 |
| --- | --- | --- |
| リスク別のレビュー強度 | 変更の危なさで、確認の厚さを変える | 危ないファイルだけ人が読む |
| Google のレビュー指針([eng-practices](https://google.github.io/eng-practices/review/reviewer/looking-for.html)) | 設計、機能、複雑さ、テスト、命名などを見る | 人は設計と機能(意図どおりか)に絞る |
| Cisco / SmartBear の調査 | 1回で読むのは 200〜400 行、60〜90 分まで。超えると見落としが増える | 1回のレビューを短く区切る |
| STRIDE | なりすまし、改ざん、否認、情報漏えい、サービス停止、権限昇格の6つで考える | 境界を見るときの問いに使う |
| OWASP Code Review Guide / ASVS | セキュリティの確認項目の一覧 | 認証やデータの部分で、抜けがないかの参照用 |

## 手順(1回 30〜60 分)

1. **起きてはいけないことを3つ書く(5分)**
   コードを見る前に、要件から書く。例:「他人の取引が見える」「金額が小数で保存される」「許可していない人がログインできる」。先にコードを読むと、コードの考え方に引っ張られる。
2. **AI に説明させる(5分)**
   次を聞く。答えは、確かめる前の主張として扱う。
   - この変更は何をするか、3行で
   - 手順1の3つは、どこで防いでいるか(ファイルと行番号)
   - この変更で一番壊れやすいところはどこか
3. **テストを先に読む(10〜15分)**
   手順1の3つそれぞれに、それを確かめるテストがあるかを見る。見つけたら「防いでいる行を消したら、このテストは落ちるか」を考える。落ちないなら、そのテストは守っていない。
4. **関所だけを1行ずつ読む(15〜20分)**
   1行ずつ読むのは次の場所だけ。それ以外は流し読みでよい。
   - 外からの値を受け取るところ(入力の検証)
   - 許可・拒否を決めるところ(認証、権限)
   - データを書く・消すところ
   - お金や数値を変換するところ
   - 権限を付ける設定、外に公開する設定、秘密情報の扱い
5. **AI の主張を2〜3個だけ確かめる(5分)**
   手順2の答えから選び、本当にそのとおりか自分で見る。1つでも違ったら、そのファイルは1行ずつ読む。
6. **実際に壊しにいく(5〜10分、できれば)**
   検証環境で、わざと悪い操作をする。例:別のアカウントで他人の取引を消す、金額に 1.5 を入れる、ログインせずに呼ぶ。
7. **判断して記録する(5分)**
   「承認」「承認して Issue を作る」「差し戻し」のどれかにする。何を確かめたかを1〜2行で残す(例:「A3 は repository の `_run` で防いでいることを確認。テスト E07 で検証済み」)。

## 領域ごとの問い

| 領域 | 問い |
| --- | --- |
| 認証 | 本人確認に使う値は、偽造できない場所から来ているか。確認に失敗したら、必ず拒否になるか |
| 権限・データ分離 | 「誰のデータか」の条件は1か所で付いていて、迂回できないか。新しい入口が増えたとき、その条件を通るか |
| 入力 | おかしな値は、保存する前に止まるか。黙って直していないか |
| お金・数値 | 小数、丸め、桁あふれ、マイナスの扱いは決まりどおりか |
| 削除・データ変更 | 間違えたら戻せるか。対象を絞る条件が抜けたら、全件に効いてしまわないか |
| インフラ・IAM | 付けた権限は必要な範囲だけか(プロジェクト全体か、リソース単位か)。外に公開される範囲は意図どおりか |
| 秘密情報 | 鍵、トークン、個人情報が、コード、ログ、ビルド設定に出ていないか |
| コスト | 呼び出し回数や処理量に上限があるか。放っておくと増え続けるものはないか |

IAM の確認では、コンソールのプロジェクトの IAM 画面にはプロジェクト単位の権限しか出ない点に注意する。リソース単位で付けた権限(Artifact Registry のリポジトリ、サービスアカウントなど)は、そのリソースの権限画面か `gcloud ... get-iam-policy` で確認する。

## AI のレビューが見落としやすいこと

- 要件とのずれ:コードとしては正しいが、やりたいことと違う
- 書かれていないもの:差分に出てこない抜け
- 実装に合わせたテスト:同じ AI が書くと、実装の間違いをテストも同じように間違える
- 設定と権限の意味:IAM や公開設定が何を許すかは、コードの外の知識が要る
- ファイルをまたぐ前提:あるファイルの前提を、別のファイルが崩している
- もっともらしい間違い:ライブラリの初期値や挙動を、それらしく誤って説明する

## やらなくてよいこと

- 上から1行ずつ全部読む
- 命名、書き方、細かいスタイルの確認
- 1回で 400 行を超えて読む
- AI の要約だけ読んで承認する(手順5で必ず一部を確かめる)

## 例:Plutus Lite の G6

起きてはいけないこと:他人の取引が見える・変えられる(A3)、許可していない人が使える(A1)、権限が必要以上に広い。

| ファイル | 関所 | 問い |
| --- | --- | --- |
| `api/app/auth/dependencies.py` | `get_current_user` | 確認に失敗したら必ず 401 か。uid はトークンからだけ来るか。メール未確認の人は 403 か |
| `api/app/repository/transactions.py` | `_run`、`_scope`、`update`、`delete` | user_id 条件の無い SQL は止まるか。更新・削除の前に自分のものか確かめているか |
| `infra/project-iam/main.tf` | プロジェクト単位の権限、シークレットの読み取り権限 | デプロイ用アカウントの権限は必要な分だけか。許可リストを読めるのは API だけか |
| `infra/cloud_build.tf` | `build_act_as` | デプロイ用アカウントがなりすませるのは、API と画面の2つだけか |
| `cloudbuild.yaml` | 置き換え変数、`deploy-api` | メールアドレスや鍵が書かれていないか。デプロイ先は検証環境だけか |

証拠:A1 は `eval/test_a1_auth.py`、A3 は `eval/test_a3_isolation.py` の E07・E08 が確かめている。
