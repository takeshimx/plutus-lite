# 半自動AI開発フライホイール 実践マニュアル(新規開発編)

対象: one-pager(要件整理済みの1枚資料)のみが存在し、ローカル環境もインフラも未整備の新規プロジェクト。リリースまでの全工程を扱う。ドメイン(野球、財務、その他)に依存しない。  
版: v0.2 / 作成日: 2026年11月5日 / ツール情報の基準時点: 2026年11月

## 結論

サイクルタイムを決めるのはコードの生成速度ではなく、人の関門を通過するまでの待ち時間である。したがって、受入条件と評価基盤を実装より先に作り、AIが自己検証できる状態にしてから実装を並列化する。人は10か所の関門に集中して判断し、それ以外はCIの合否で自動的に次工程へ進める。

本書は、この考え方を11の工程、10の関門、ツール構成、ドメイン別の適用方法、テンプレートにまとめたものである。新規プロジェクトごとに、工程表を上から順に進め、付録のテンプレートをコピーして使う。稼働中のプロダクトへの機能追加と改修は、姉妹編の「既存プロダクト向け」を参照する。

## 前提とする入力

one-pagerには次の項目が含まれていること。不足があれば工程P1で補う。

- 解く課題と利用者
- 成功指標(測定方法を含む)
- スコープ内と、やらないこと
- 制約(予算、期限、規制、利用できるクラウド)
- ドメイン用語と、データの入手元

## 設計原則

- 検証手段を先に作る。受入条件、テスト、評価ゲートがない状態で実装を始めない。
- 作成者と検証者を分ける。レビューは実装とは別のセッションで行い、可能なら別のモデルを使う。同じ文脈を持つエージェントは同じ見落としをする。
- 人の関門は少数に絞り、合否基準を事前に文書化する。基準のない関門は、気分による承認になる。
- エージェントの権限は最小にする。検証環境のみ書き込み可とし、予算上限と実行回数の上限を設ける。
- 決定はすべてADR(設計判断記録)とPRに残す。翌朝に結果を見る人が、理由を追える状態にする。
- プロダクト自体にLLMを使う場合、金額、集計、権限判定のような毎回同じ結果になる処理はコードが行い、LLMは解釈と探索に限定する。

## 人の関門と合否基準

人が確認する対象と、合格とする基準を事前に決めておく。却下した場合は、理由を該当のIssueまたはADRに記録し、AIにやり直させる。

| 関門            | 確認対象                                                 | 合格基準                                                                                  |
|-----------------|----------------------------------------------------------|-------------------------------------------------------------------------------------------|
| G0 準備         | 契約、請求、予算、権限                                   | 予算アラートと上限が設定済み。エージェントに渡す権限が検証環境のみ                        |
| G1 スコープ     | PRD、受入条件、質問リストへの回答                        | 受入条件がすべてテスト可能。やらないことが明記されている                                  |
| G2 設計         | ADR、データモデル、コスト試算                            | 選定理由と却下理由がある。月額コストが予算内。データモデルの変更コストを理解した上で承認  |
| G3 規約         | CLAUDE.md / AGENTS.md、CODEOWNERS、ブランチ保護          | 高リスクパスが指定済み。直接pushが禁止されている                                          |
| G4 インフラ     | terraform planの差分                                     | 削除と置換が意図したものだけ。データを持つリソース、公開範囲、IAMの変更を1件ずつ確認済み  |
| G5 評価基準     | golden set、評価指標、judgeの出力                        | 正解ラベルを人が確認済み。judgeと人の判定が一致する事例の割合を測定し、許容値を決めている |
| G6 高リスク差分 | 権限、課金、データ移行、IaC、秘匿情報、外部公開APIの変更 | 差分を人が読み、意図と一致。テストが変更の意図を実際に検査している                        |
| G7 受入         | 受入条件の達成状況レポート、実データでの動作             | 全条件を満たしている。または、満たしていない条件の合意済みリスクが記録されている          |
| G8 本番反映     | リリース計画、ロールバック手順、不可逆変更               | ロールバックが実演済み。不可逆変更には事前バックアップがある                              |
| G9 運用判断     | 障害の原因、再発防止策、改善の優先順位                   | 原因が再現または証拠で確認されている。優先順位が成功指標と結びついている                  |

## レビュー強度の分類

すべてのPRを全文読むと、人のレビュー待ちが開発全体の遅れの原因になる。変更の種類ごとに確認の厚さを変え、変更するファイルの場所と変更の種類に応じて、CODEOWNERSとブランチ保護で必ず守らせる。

| 区分     | 対象の例                                                                                          | 人の関与                                                     |
|----------|---------------------------------------------------------------------------------------------------|--------------------------------------------------------------|
| 低リスク | ドキュメント、軽微なUI文言、テスト追加のみの変更                                                  | 要約とCI結果を確認して承認                                   |
| 中リスク | 業務ロジック、画面遷移、集計処理、依存関係の更新                                                  | レビューエージェントの指摘への対応を確認し、主要な差分を読む |
| 高リスク | 認証と権限、課金、データ移行とスキーマ変更、IaC、秘匿情報、金融データやSQLの安全装置、外部公開API | 人が差分を細かく読む。必要に応じて動作確認を実施             |

## ドメイン別の適用

工程と関門はドメインに依存せず、変わるのは「正解の定義」と「高リスク領域」である。次の表は、これまでの2つのプロジェクトを例に、新規ドメインで何を決めるかを示す。

| 決める項目                   | 野球分析(Diamond Lens)                                 | 個人財務(Plutus)                                                | 新規ドメインでの決め方                                                            |
|------------------------------|--------------------------------------------------------|-----------------------------------------------------------------|-----------------------------------------------------------------------------------|
| 評価の正解                   | 統計値と、質問に対する整理出力の一致                   | SQLの実行結果(件数、金額)の一致。SQL文字列では比較しない        | 機械的に比較できる正解を先に定義する。定義できない部分は、人のラベルとjudgeで補う |
| 毎回同じ結果になる処理の範囲 | LLMは引数を出力し、SQLの生成と実行はコードが実行       | 金額と日付の照合はPythonが担当。LLMは一致しなかった分の調査のみ | 数値、権限、課金にかかわる処理はコード側に置く                                    |
| 高リスク領域                 | プロンプトインジェクション、範囲外の質問、トークン予算 | 利用者ごとのデータ分離、SQLの安全装置、為替など範囲外の数値     | 誤りが金銭、個人情報、不可逆な操作につながる箇所を列挙し、G6の対象にする          |
| 異常時の方針                 | 範囲外の質問は拒否または限定回答                       | 範囲外の値は書き込まず処理を中止する                            | 誤った出力より、停止と通知を優先する箇所を決める                                  |
| フィードバックの経路         | 評価ボタンからレビュー待ちを経てgolden setへ           | 修正内容からルール案を作成し、承認後に反映                      | 運用中の訂正を、人の承認を挟んでgolden setに戻す経路を作る                        |

## 運用指標

リリースごとに次の指標を記録し、関門の合否基準とレビュー強度の分類を更新する。目標値は、最初の3サイクルの実測値を見て決める。

- リードタイム: Issue起票から本番反映まで
- PR1件あたりの人のレビュー時間
- 評価ゲートの不合格率と、不合格の原因
- 手戻り率: マージ後に修正PRが必要になった割合
- 本番障害の件数と、検知までの時間
- PR1件あたりのエージェント実行コスト

## 失敗パターンと対処

| 症状                                   | 原因                                                       | 対処                                                   |
|----------------------------------------|------------------------------------------------------------|--------------------------------------------------------|
| 動くが意図とずれた機能が上がってくる   | 受入条件が曖昧、または暗黙の前提が未記載                   | G1に戻り、ずれた箇所を受入条件とテストに追加する       |
| テストがすべて通るのに不具合が出る     | AIが、自分の実装に合わせたテストを書いている               | 変異テストの導入。テスト意図を人がG5とG6で確認する     |
| レビューの指摘が毎回同じ見落としをする | 実装と同じ文脈、同じモデルでレビューしている               | 別セッション、可能なら別モデルに切り替える             |
| 人のレビューがたまる                   | 全PRを同じ強度で読んでいる                                 | レビュー強度の分類を見直し、低リスクを要約確認に移す   |
| コストが想定を超える                   | エージェントの実行回数、スキャン量、環境の放置に上限がない | 実行ターン数、スキャン量、月額の上限をP0とP3で設定する |
| 評価ゲートが役に立たなくなる           | 基準の緩和と、golden setの更新が止まっている               | 運用の学習段階で、障害事例を必ずgolden setに追加する   |
| エージェントが想定外の操作をする       | 権限が広い                                                 | 最小権限に絞り、本番への書き込みを人の承認経由に限る   |

## 付録A: CLAUDE.md / AGENTS.md の骨子

    # プロジェクト概要
    目的、利用者、成功指標(one-pagerへのリンク)

    # 開発コマンド
    セットアップ / テスト / lint / 型検査 / 評価ゲート の実行コマンド

    # PRのルール
    - 1PRは1つの受入条件に対応する
    - 変更理由と確認方法をPR本文に書く
    - テストを同じPRで追加する
    - 完了条件: CIと評価ゲートが通過していること

    # 触ってはいけない領域(人の承認が必要)
    - 認証と権限 / 課金 / スキーマ移行 / IaC / 秘匿情報

    # コーディング規約
    言語、命名、エラー処理、ログの方針

    # 判断に迷ったとき
    実装を止めて、Issueにコメントで質問する
